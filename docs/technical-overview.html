The problem

LLMs have no memory between conversations. Every question is a blank slate. The industry's default answer is retrieval-augmented generation (RAG) — but RAG is a search engine bolted onto a chatbot, not a memory.

A vanilla RAG pipeline does one thing well: given a question, find documents that look similar, and hand them to the LLM. It has no concept of time, no notion of importance, no ability to learn from being right or wrong, and no way to notice when new information contradicts what it said last week. It answers your question today the same way it would have answered last month, even if you've told it three times that things changed.

The core issue

A software engineering agent that hits the same bug pattern for the tenth time should be smarter about it the tenth time than it was the first. RAG makes it exactly as smart every time.

What human memory does that RAG doesn't

Timeline

You remember when something happened, and in what order. RAG has no sense of "before" or "after."

Importance

Some memories matter more than others — critical facts vs. small talk. RAG treats every document equally.

Strengthening

Memories you use often become more accessible. RAG doesn't know which document you use most.

Decay

Stale memories fade into the background — but stay recoverable if needed. RAG has no forgetting curve.

Association

Ideas remind you of other ideas. RAG returns islands, not networks.

Conflict

When new information contradicts old, human memory notices. RAG silently returns whichever matches better.

The solution

NeuroMem is a memory engine that gives an AI agent all six of those properties. It stores different kinds of memory, connects them into a graph, ranks retrieval by six independent signals, strengthens what gets used, fades what doesn't, and — crucially — never silently overwrites a conflicting fact.

The research question

Can an agent with structured, consolidating, associative, decaying memory behave more effectively than an agent using conventional vector RAG alone?

The project is a full proof-of-concept: a running FastAPI backend, an OpenSearch cluster storing the memories, a LangGraph agent that talks to the memory engine, an async worker that consolidates conversations into durable facts, a Streamlit dashboard for humans to inspect the whole system, and a benchmark harness that A/B tests NeuroMem against plain RAG on realistic scenarios.

The memory model

NeuroMem stores three kinds of memory, plus a graph of relationships between them. This mirrors the distinction cognitive science draws between episodic, semantic, and procedural memory — though the goal here is useful engineering behaviour, not biological accuracy.

Episodic — "something that happened"

A specific event with time and context. When you tell the agent "we deployed v4.7 this morning at 9am," that becomes an episodic memory. Every agent turn is also stored as an episodic memory — the raw record of the interaction, which later becomes the source of consolidation. 

{
  "id": "epi_01M03F76P3SQW09FAPR1Z5CZ55",
  "memory_type": "episodic",
  "content": "OpenSearch deployment failed because vm.max_map_count was set to 65530.",
  "event": "opensearch_failure",
  "event_timestamp": "2026-08-15T14:07:00Z",
  "importance": 0.85,
  "confidence": 0.95
}

Semantic — "something durable that's true"

A generalised fact, extracted from one or more episodic events. Where episodic memories are dated and specific, semantic memories are stable. "The user prefers Rust for new microservices" is semantic. "The user said on Tuesday they prefer Rust" is episodic.

Procedural — "how to do something"

A reusable procedure — how to fix a bug, how to deploy a service, how to run a test suite. Includes ordered steps, preconditions, and — critically — success_count, failure_count, and success_rate. A procedure that has worked 15 times ranks higher than one that has failed 3 times.

Relationships — "how ideas connect"

Every memory can be linked to any other memory via one of ten relationship types. This is the graph that turns memory from a bag of documents into an associative structure.

The retrieval pipeline

When a query comes in, NeuroMem doesn't ask "which document is most similar?" It asks six different questions and blends the answers. This is the core of what makes it not-RAG.

query text | v +------+------+ +---------------------+ | embed query | | Full agent context | | (OpenAI 3- | | passed to the LLM | | large) | +---------^-----------+ +------+------+ | | | v | +------+---------------------------+-----+ | semantic search (k-NN, OpenSearch) | | keyword search (BM25 multi_match) | | union candidates by memory ID | +------+----------------------------------+ | v +------+----------------------------------+ | fetch full documents via mget | | fetch relationships for candidate set | | compute 6 signal scores per memory | | weighted sum → final score | +------+----------------------------------+ | v top-K with Explanation object attached

The six signals

SignalWeightWhat it measures
semantic0.40Cosine similarity via OpenSearch k-NN on 3072-dim OpenAI embeddings
keyword0.15BM25 match on content and type-specific fields, normalised by the result set max
importance0.20Author-supplied score reflecting how much this memory should matter
recency0.10exp(-λ · age_days) since created_at
activation0.10activation · exp(-λ · age_days_since_last_access)
relationship0.05Boost when two candidates share an edge in the graph
score = semantic × 0.40 + keyword × 0.15 + importance × 0.20 + recency × 0.10 + activation × 0.10 + relationship × 0.05
Explanation is a feature, not a debug field

Every recall response includes an Explanation object showing all six component scores per result, plus the weights that produced the final score. The Retrieval Trace tab in the dashboard renders these as a bar chart. You can always answer "why did that memory win?"

Cognitive lifecycle

Retrieval isn't just a read operation — it's a signal that a memory was useful. NeuroMem uses that signal in two ways: strengthening what gets used, and decaying what doesn't.

Strengthening (§18 of the plan)

After every recall, the top-K memories have their activation bumped and access_count incremented. This is a fire-and-forget background task — the API response returns immediately, and the strengthening happens on the next tick via an OpenSearch bulk painless script that updates all top-K memories in a single round-trip. 

ctx._source.activation = Math.min(1.0, ctx._source.activation + params.bump);
ctx._source.access_count = ctx._source.access_count + 1;
ctx._source.last_accessed_at = params.now;

Decay (§19 of the plan)

Decay is computed at query time, never persisted. During ranking, the activation signal is multiplied by an exponential decay factor based on time since last access. A memory that was strong last year but has never been retrieved since will have a low effective activation today — but its stored activation field is unchanged.

effective_activation = activation × exp(−λ × days_since_last_access)
No deletes, ever

Superseded, contradicted, and decayed memories all stay queryable. The ranking is the only lever — old memories just get pushed down. A dashboard can filter or highlight them; a research script can dig them up for postmortem inspection.

Consolidation

Not every conversation deserves permanent memory. Consolidation is the step where an LLM looks at a completed agent turn and decides what — if anything — is worth remembering forever.

The pipeline

  1. The agent finishes a turn. Its extraction node emits a list of MemoryCandidate objects — each classified as EPISODIC, SEMANTIC, PROCEDURAL, or IGNORE.
  2. The turn itself is persisted as a single source EpisodicMemory — this is what derived memories will point to via DERIVED_FROM.
  3. For each non-IGNORE candidate, NeuroMem searches the existing memory graph for semantically-similar existing memories.
  4. If any are close enough, a second LLM call adjudicates — is the new candidate a DUPLICATE, does it SUPERSEDE the existing one, does it CONTRADICT it, or is it INDEPENDENT?
  5. Duplicates are skipped. All other outcomes create a new memory row plus the appropriate relationship edge to the pre-existing one. The old memory is never modified.
  6. Every new memory also gets a DERIVED_FROM edge back to the source turn — one hop always gets you from a fact to the conversation that produced it.
Never overwrite

When you say "I switched to Qdrant," NeuroMem doesn't delete the old "prefers OpenSearch" fact and replace it. It creates a SUPERSEDES edge from the new memory to the old. Both stay in the graph. Ranking pushes the old one down; the dashboard can display the transition; a future query can walk backwards through the history if it needs to.

Async and non-blocking

Consolidation runs in the background so the user gets their response immediately. When you chat with the agent, the response comes back after the answer node finishes; a fire-and-forget task pushes the extracted candidates onto an asyncio.Queue, and a worker drains it. Errors in consolidation never fail the user's turn.

The agent loop

The agent is a LangGraph state machine with seven nodes. Each node reads and writes to a shared AgentState dictionary. The graph shape matches the plan §12 exactly — three of the nodes are passthroughs in the current phase (reserved for future tool use), but the plumbing is in place.

Extraction never persists

The plan is explicit: the LLM must never directly write to storage. It only proposes. The Memory Engine validates and persists — that separation of concerns is enforced by keeping extraction and consolidation in separate processes with a queue between them.

Technology stack — what each thing does and why

Python 3.12

Modern type hints (Literal, discriminated unions), match statements, strict async/await. Chosen for the depth of ML/LLM library support and the plan's explicit constraint.

FastAPI

Async HTTP framework with automatic OpenAPI generation. Every route is Pydantic-validated on both request and response. The lifespan context manager owns the OpenSearch client, OpenAI client, and the consolidation worker task.

Pydantic v2 (with extra="forbid")

Every domain model rejects unknown fields. This mirrors OpenSearch's dynamic: strict mapping so schema drift fails fast at both edges. Discriminated unions on memory_type let a single POST /memory/store handler serve all three types.

OpenSearch (k-NN plugin)

Four indexes on a 3-node cluster: episodic, semantic, procedural, relationships. k-NN vector search for semantic similarity, BM25 multi_match for keyword, bulk painless scripts for atomic strengthening writes, aggregations for dashboard stats. Chosen over pgvector or Qdrant for the first-class hybrid search story.

LangGraph

Node-based state machine with typed AgentState as a TypedDict. Each node is an async closure that reads and writes state. Version 1.x's type system fights us occasionally, but the runtime is exactly what a memory-driven agent needs.

OpenAI API

Two chat models: gpt-4o-mini for classification and extraction (JSON mode, temp=0), gpt-4o for reasoning and answer generation. One embedding model: text-embedding-3-large at native 3072 dimensions. Same async client instance is shared across chat and embeddings.

Streamlit + pyvis

Six-tab dashboard talking only over HTTP. Overview (stats cards), Memory Explorer (search + inspect), Graph (pyvis network with color-coded types), Timeline (chronological table), Retrieval Trace (per-signal contribution bar chart), Consolidation Trace (dynamic candidate editor).

uv + pyproject.toml

Modern Python packaging. Single lockfile, hermetic sync, ARM-friendly for Jetson deployment. ruff for lint + format, mypy in strict mode for typechecking, pytest for the test suite.

ULID + prefix routing

Memory IDs are ULID-based with a type prefix: epi_, sem_, pro_, rel_. A pure string function routes any ID to the correct OpenSearch index — no lookup roundtrip needed.

structlog

Structured JSON logs with contextvars for request_id, agent_id, and memory_id. Every memory lifecycle event produces a structured log line, feeding future observability tooling.

Async everywhere

aiohttp-backed OpenSearch client, async OpenAI client, async FastAPI, async LangGraph nodes, asyncio.Queue for the consolidation worker. Fire-and-forget tasks tracked in a set so they can't be garbage-collected mid-execution.

Docker Compose

Two-service deployment on the Jetson: memory_api and dashboard. Both point at the externally-provisioned OpenSearch cluster on the OptiPlex via LAN. No infrastructure duplication.

Evaluation — does it actually work?

The whole point of the project is to answer whether NeuroMem beats vanilla RAG. Phase 6 built an A/B benchmark harness that runs the same scenarios through both approaches and produces a markdown report.

The harness

Scenarios live as YAML files under experiments/scenarios/. Each scenario declares a set of memories to seed, optionally a set of relationships to create between them, and a list of queries with expected outcomes (substring-based). The runner:

  1. Generates a unique run_id for isolation (marker is templated into every memory + query).
  2. Seeds all memories via the real MemoryService.create_memory — auto-embeds via OpenAI.
  3. Seeds all relationships via create_relationship.
  4. Runs each query through both modes:
    • rag mode: naive k-NN semantic search only, then LLM answer.
    • neuromem mode: full 6-signal MemoryService.recall, then identical LLM answer prompt.
  5. Scores each result on 8 metrics: precision_at_k, recall_hit, top1_match, answer_hit, forbidden-substring detection, count of irrelevant retrievals, retrieval latency, and answer latency.
  6. Writes a timestamped markdown report with aggregate stats + per-query detail + sample answers.

Where NeuroMem wins clearly

Multi-hop reasoning queries — where the answer requires connecting distant memories through the relationship graph. On q7 of scenario 012 ("how were the mTLS cert issue and the Redis outage connected?"), NeuroMem's precision was double RAG's, and its answer used the exact synthesized phrase "compound root cause" from the semantic memory, while RAG paraphrased from raw episodic events.

Where NeuroMem regressed

Timeline / sequence questions. On q4 of scenario 012 ("what order were the layers discovered?"), the activation-based ranking demoted the oldest event (mTLS) out of top-8. This is a real weakness — the current lifecycle-aware ranking penalises exactly the memories a "what happened first" query needs. The fix is per-query weight overrides, which is a documented next step.

The load-bearing design decisions

Ten decisions that shape everything else in the system. Each of these has downstream consequences that would be expensive to revisit.

  1. Never overwrite a memory. Conflicting facts get SUPERSEDES or CONTRADICTS edges; the old row stays queryable. Decay is query-time only. No deletes, ever.
  2. ULID-prefixed IDs (epi_, sem_, pro_, rel_) route to the correct index as a pure string function. No lookup roundtrip.
  3. extra="forbid" on every Pydantic model mirrors OpenSearch's dynamic: strict mapping. Schema drift fails fast on both sides.
  4. Discriminated union for Memory on memory_type. One endpoint serves all three types; TypeAdapter dispatches on read.
  5. Explanation is a first-class field, not a debug hint. The dashboard's Retrieval Trace tab renders per-signal contributions directly from it.
  6. Bulk painless _bulk script for strengthening: one round-trip bumps activation + access_count + last_accessed_at atomically per doc.
  7. Two-model LLM adapter, one client: gpt-4o-mini for extraction/classification (JSON mode, temp=0), gpt-4o for reasoning.
  8. Route ordering matters in FastAPI. Literal /memory/stats and friends declared before /memory/{memory_id} to avoid the wildcard swallowing them.
  9. Evaluation isolation via per-run {run_id} markers in seeded memory content, not deletes. Runs coexist forever; the report includes the run IDs so you can dig up any specific one.
  10. The agent depends on MemoryService, not MemoryStore. Storage can be swapped without touching the graph, and consolidation reuses the same facade the routes see.

What's next

The POC is feature-complete against its plan. The natural extensions fall into three categories.

Deeper reasoning

Multi-hop relationship traversal beyond depth 3. Cross-encoder reranking for the top-K. Learned or RLHF-tuned ranking weights instead of the fixed baseline. Per-query weight overrides so scenarios can specify "for this question, downweight activation."

Better isolation

Multi-tenant memory scoping (currently single global pool). Per-repository memory namespaces for a software-engineering agent. Automatic pruning of stale eval-run memories to keep the shared cluster clean.

Domain adaptation

The scenarios already lean toward software debugging. Adding a diagnose endpoint that takes an error message + stack trace + repo context and returns ranked fix procedures with success rates would turn this into a real coding-agent memory backend.

Beyond OpenAI

Every LLM and embedding call is behind a Protocol. Swapping to a local model on the Jetson (llama.cpp, vLLM) is a two-file change. The plan explicitly reserves this direction.
